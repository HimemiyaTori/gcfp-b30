## 1. 项目概述

本项目用于管理《Groove Coaster: Future Performers》（以下简称 FP）的个人成绩。

一期目标以“快速录入成绩 + 基础 Rating / B30 查看”为核心：用户上传游戏成绩截图，系统通过 OCR 自动识别曲目与 Score，识别成功后直接写入本地数据库。Rank 与单谱 Rating 均由 Score 和谱面信息自动推导，用户如发现识别错误，可在成绩管理页面中事后修改 Score、FC / AP 与 Max Chain；曲目、模式和难度不可通过编辑更换。

一期同时完成 Groove Rating 计算和简单 B30 列表展示。二期再增加 B30 成绩图、Excel 导入导出、历史变化等扩展功能。

项目采用纯前端 Web 架构，尽量避免不必要的后端服务与复杂依赖。PWA 仅作为二期之后的未来设计选项，不属于一期或二期的交付范围。

## 2. 项目目标与边界

### 2.1 一期目标

一期实现以下功能：

1. 上传一张或多张 FP 成绩截图。
2. 使用 OCR 识别截图中的：
    - 曲目名称
    - Score
    - 难度 / 谱面信息（根据实际截图结构决定最终识别字段）
3. 根据 OCR 曲名在本地曲库中进行模糊匹配。
4. OCR 成功后直接写入本地数据库。
5. 不提供“录入前确认/修改”步骤。
6. 在成绩管理页面中支持手动新增与事后修改，二者一并实现，录入 / 修改字段包括：
    - Score、FC / AP、可选 Max Chain
7. Rank 不允许用户修改，统一根据 Score 自动推导。
8. 根据 Score 与谱面等级自动计算单谱 Rating。
9. 计算 Groove Rating，并提供简单 B30 列表展示。
10. 支持成绩搜索、筛选与删除。
11. 一期仅提供简体中文 UI，预留国际化结构；日文、英文、繁体中文 UI 二期交付。
12. 支持浅色、深色、跟随系统主题。
13. 支持曲目名称和歌手信息在日文 / 英文之间切换。
14. 截图仅在 OCR 处理期间驻留内存，不做任何持久化；只持久化结构化成绩数据。
15. 一期 OCR 仅在识别页运行，离开页面即取消；一期不引入 Pinia，跨页面后台队列留到二期评估。

### 2.2 二期目标

二期及后续计划实现：

1. B30 成绩图生成与导出。
2. Excel 导入。
3. Excel 导出。
4. Rating 提升空间分析。
5. 更完整的曲目信息查询与统计。
6. 历史成绩 / Rating 变化记录（具体数据模型与交互待后续单独设计）。
7. 根据实际需求完善 OCR 后台任务队列。
8. 如有明确跨页面全局状态需求，再正式引入 Pinia。
9. 交付日文、英文、繁体中文 UI。

### 2.3 暂不实现

一期暂不实现：

- 登录 / 注册
- 云端数据库
- 多设备同步
- 好友系统
- 在线排行榜
- 应用层 OpenCV.js 图像处理（OCR SDK 内部依赖除外）
- 歌曲封面比对
- Excel
- B30 成绩图生成
- ECharts 图表
- 服务端 OCR
- 独立曲库查询页（一期仅复用曲库支持搜索和选谱）
- PWA（仅作为二期之后的未来设计选项）

### 3.3 图像预处理使用 Canvas

一期识别目标均为文字和数字，并且 FP 成绩截图 UI 结构相对固定。

一期图像处理需求主要为：

- 按归一化坐标裁剪固定区域
- 缩放识别区域
- 将裁剪结果转为 Canvas / ImageData

上述应用层预处理均由 Canvas 完成。阶段 5 使用的官方 PaddleOCR.js 0.4.2 SDK 内部依赖 OpenCV.js 和 ONNX Runtime；允许其作为 OCR 运行时传递依赖，不增加应用层 OpenCV 图像处理代码。

只有以后出现以下需求时再考虑：

- 非标准截图、裁切截图
- 拍照导致的透视变形
- 旋转校正
- 二值化、锐化、去噪
- 模板匹配
- 复杂封面视觉匹配

## 4. UI 与状态管理设计

### 4.1 UnoCSS 与 Naive UI 分工

UI 以 UnoCSS 为主。

UnoCSS 负责：

- 页面整体布局
- 导航
- 卡片
- 标题
- 间距
- 响应式布局
- 亮 / 暗主题下的主要视觉样式

Naive UI 仅按需用于复杂交互组件，例如：

- `NDataTable`
- `NSelect`
- `NInputNumber`
- `NModal`
- `NMessage`
- `NPopconfirm`
- `NSpin`

简单按钮、卡片、标签等优先自行使用 Vue + UnoCSS 实现，避免网站整体呈现典型后台管理系统风格。

### 4.2 一期状态管理策略

一期不引入 Pinia。

初期状态可按以下方式管理：

- 页面局部状态：Vue `ref` / `reactive`
- 可复用逻辑：Composable
- UI 语言：vue-i18n 自身状态 + localStorage
- Theme / 曲目信息显示语言：轻量 `useSettings()` composable + localStorage
- 成绩数据：Dexie / IndexedDB
- OCR 当前页面任务：`useOcrImport()` composable

建议结构：

```text
composables/
├─ useSettings.ts
├─ useScoreList.ts
└─ useOcrImport.ts
```

一期 OCR 任务与识别页生命周期绑定。离开识别页时取消当前未完成任务及排队任务，释放截图相关内存；已成功入库的成绩保留。取消后返回的识别结果不得继续入库。刷新或关闭页面不恢复任务。

跨页面 OCR 后台队列及 Pinia 留到二期评估。

### 4.3 成绩数据不进入全局状态副本

无论后续是否引入 Pinia，成绩持久化数据都由 Dexie / IndexedDB 负责。

不维护：

```text
Dexie Scores
+
Pinia Scores[]
```

两套成绩副本。

成绩数据的唯一真实来源应为 IndexedDB。

## 5. 国际化与主题

### 5.1 UI 国际化

使用 `vue-i18n`，一期仅交付简体中文翻译，预留国际化结构。日文、英文、繁体中文 UI 在二期交付。

未手动选择 UI 语言时，根据浏览器 / 系统提供的用户语言动态匹配当前已交付的语言：简体中文对应 `zh-CN`，繁体中文对应 `zh-TW`，日语对应 `ja-JP`，英语对应 `en-US`；未支持的语言回退英语。一期仅显示简体中文，二期随用户语言匹配上述四种 UI。用户手动设置后优先使用并持久化该设置。

目录：

```text
src/locales/
├─ zh-CN.json  # 一期交付
├─ zh-TW.json  # 二期交付
├─ ja-JP.json  # 二期交付
└─ en-US.json  # 二期交付
```

### 5.2 曲目信息语言

曲名与歌手信息不使用 vue-i18n 翻译文件，而来自曲库数据。

未手动选择曲目信息语言时，按UI语言独立决定默认值：简体中文、繁体中文、日语UI默认日语，英语UI默认英语。用户手动选择日语 / 英语后，优先使用并持久化该设置。

曲目信息类型见第 6.2 节，统一通过 helper 获取，如：

```ts
getSongTitle(song, lang)
getSongArtist(song, lang)
```

曲库保证 `title.ja`、`artist.ja` 存在；英文 `en` 可选，未提供时展示日文原名。`vocal` 可选，无演唱者时省略；不编造英文译名或演唱者。

### 5.3 主题

主题默认跟随系统（System）；用户手动选择后持久化该设置。

主题选项：

```text
Light
Dark
System
```

UnoCSS 使用 `dark:` 处理主要样式。

当选择 `system` 时，通过：

```ts
window.matchMedia('(prefers-color-scheme: dark)')
```

获取实际主题。

Naive UI 的 theme 同步跟随最终解析出的亮 / 暗状态。

### 5.5 动画规范

当前采用 Vue 内置 Transition + CSS 过渡，暂不增加第三方动画库。卡片数量增加时复用统一动画组件，避免每张卡片单独定义时长和缓动。若后续确需弹簧、拖拽或复杂布局重排，再评估适配 Vue 的动画库。

- `src/components/common/CardTransition.vue`：共用卡片／通知进出场组件。卡片默认轻微上移加淡入；通知桌面端从右侧移入并淡入，手机端从顶部移入；自动消失与手动关闭共用离场动画。
- `src/components/common/AnimatedProgress.vue`：通过 `transform: scaleX()` 平滑推进，保留 progressbar 语义和实际已处理数量，不通过虚假进度模拟识别工作量。
- 时长统一定义在 `src/components/common/motion.ts`：入场 280 ms、离场 180 ms、进度推进 400 ms。缓动与位移规则集中在 `src/motion.css`，按需使用，不对所有卡片后代自动施加动画。
- 全成功后等待最后一段进度过渡完成再关闭识别弹窗，并显示完成通知；关闭弹窗或切页仍取消后续回调。失败结果继续保留弹窗。
- 尊重 `prefers-reduced-motion`：减少动态效果时立即更新进度和通知，取消位移、缩放及不必要的完成等待。

参考核对日期：2026-09-22。

- [Nageki 欢迎页](https://next.nageki-net.com/net/welcome)：公开构建样式包含 CSS `cardEnter`、`fadeIn`、`slideIn` 等动画；仅据可检查的公开样式描述，不据此断言整个网站未使用其他动画方案。
- [落雪 AnimatedGrid 源码](https://github.com/Lxns-Network/maimai-prober-frontend/blob/main/src/components/AnimatedGrid.tsx)：使用 `motion/react` 做淡入，结合原生 `Element.animate()` 和 FLIP 思路处理卡片重排，示例时长 300 ms。其 React 组件不直接引入本 Vue 项目。
- [Vue Transition 文档](https://vuejs.org/guide/built-ins/transition)：支持复用进出场过渡组件；当前需求采用该方案。

## 6. 曲库设计

### 6.1 曲库用途

曲库不仅用于 OCR。

一期及后续至少用于：

1. OCR 曲名匹配。
2. 成绩页搜索。
3. 手动新增时从完整曲库选谱；编辑时仅选择已有成绩并修改 Score、FC / AP 与 Max Chain。
4. 后续曲目信息查询（一期无独立曲库页）。
5. Rating 计算时读取谱面等级。
6. 后续 B30 展示。

### 6.2 结构

```ts
interface Song {
    id: string

    title: {
        ja: string
        en?: string
    }

    artist: {
        ja: string
        en?: string
    }

    // 没有演唱者信息时省略此字段，不保留空对象
    vocal?: {
        ja: string
        en?: string
    }

    // 封面原始来源 URL，来源规则见 Song.coverSourceUrl
    coverSourceUrl: string

    // 项目本地封面路径，文件名使用歌曲 ID，暂定测试用
    coverUrl?: string

    // 部分歌曲有 BPM 范围，此时 bpm 作为最小值。若 bpmMax 不存在表示 BPM 固定。
    bpm: number
    bpmMax?: number

    // 歌曲分类，保存固定 ID
    genre:
        | 'anime-pop'
        | 'vtuber'
        | 'virtual-singer'
        | 'touhou'
        | 'music-game'
        | 'original'

    // 曲包：不存在时属于游戏内免费曲包；为"story"则是剧情解锁，其他值为 DLC 曲包名称
    pack?: string

    // 歌曲更新时间，不存在为游戏发售时即有，一般格式为"DLC Update #3: 2025-11-13"或"Free Update #9: 2026-08-06"
    updateAt?: string

    searchAliases?: string[]

    charts: Chart[]
}

interface Chart {
    id: string
    difficulty: 'easy' | 'normal' | 'hard' | 'master'
    mode: 'basic' | 'advanced'
    level: number
    target?: number
    special?: number
    combo?: number
    note?: number
    goldNote?: number
    hold?: number
    goldHold?: number
    arrow?: number
    goldArrow?: number
    square?: number
    goldSquare?: number

    // adv 专用
    advNote?: number
    blueNote?: number
    redNote?: number
    advHold?: number
    advArrow?: number
    blueArrow?: number
    redArrow?: number
}
```

level 为谱面定数表示；整数代表普通等级，.5 代表游戏中的 + 等级。除明确展示定数的场景，UI 展示时要将 N.5 格式化为 N+。

#### Song.genre：歌曲分类

`genre` 为必填字段，保存以下六种分类的固定 ID。曲目分类名称根据曲目信息语言设置在日文与英文之间切换，同一歌曲的所有谱面共用该分类。

| genre 值      | 日文名称               | 英文名称             |
| ---------------- | ---------------------- | -------------------- |
| `anime-pop`      | アニメ・ポップス       | Anime / Pop          |
| `vtuber`         | VTuber                 | VTuber               |
| `virtual-singer` | バーチャル・シンガー   | Virtual Singer       |
| `touhou`         | 東方アレンジ           | Touhou Project       |
| `music-game`     | 音楽ゲーム・バラエティ | Music Game / Variety |
| `original`       | オリジナル             | Original             |

#### Song.pack：所属曲包

`pack` 表示歌曲所属的曲包，与 `genre` 歌曲分类是两个独立属性。

- `pack` 为空（未提供该可选字段或值为空字符串）时，表示歌曲属于游戏内的免费曲包。
- `pack` 为 "story" 时，表示歌曲为剧情解锁曲目。
- `pack` 有值时，其值为该歌曲所属的 **DLC 曲包名称**。
- 当前类型为可选字符串 `pack?: string`；不使用 `null` 表示空值。

#### Song.coverSourceUrl：封面来源

- coverSourceUrl 保存封面原图的来源 URL；coverUrl 保存项目本地图片路径，格式为 /images/song-covers/{id}.{ext}，图片文件按歌曲 ID 命名。
- 本体歌曲封面取自 TAITO 官方 Groove Coaster Future Performers 音乐页（https://groovecoaster.com/fp/music.html）对应的歌曲图片。
- DLC 歌曲封面取自 GrooveCoaster Wiki（https://groovecoaster.link）对应歌曲的 jacket 图片。

## 7. Fuse.js 设计

Fuse.js 在一期即引入。

主要用途：

### 7.1 OCR 曲名匹配

OCR 文本可能存在：

- 少字
- 多字
- 字符误识别
- 标点差异
- 空格差异

流程：

```text
OCR 原始曲名
    ↓
normalize
    ↓
Fuse.js 搜索 songs
    ↓
候选曲目
    ↓
业务规则校验
```

## 8. OCR 设计

### 8.1 原则

一期 OCR 目标不是实现通用图片识别，而是针对 FP 固定成绩 UI 进行结构化识别。

不要：

```text
整张截图 → OCR → 从所有文字中猜字段
```

而是：

```text
截图
 ↓
Canvas 按固定比例裁剪 ROI
 ↓
分别识别各字段
 ↓
字段级 Parser
 ↓
曲库匹配 / 规则校验
 ↓
入库
```

### 8.2 ROI 坐标

裁剪坐标使用 0~1 的归一化比例：

```ts
interface Rect {
    x: number
    y: number
    width: number
    height: number
}
```

不同分辨率但同 UI 比例的截图可以复用同一套规则。

### 8.3 字段解析

每类字段应有独立 Parser。

#### Score

仅允许：

```text
0-9
,
```

可根据 OCR 常见错误进行纠正，例如：

```text
O → 0
I / l → 1（仅限数字字段）
```

最终转换为整数，并校验 `0 <= score <= 1,050,000`。OCR 识别出的 Score 超出范围时判定为识别失败，不入库，不截断为边界值。手动新增与编辑使用相同的整数及范围校验，不合法时不允许保存。

#### Rank

Rank 不进行 OCR，不允许用户编辑，也不作为独立持久化字段。

统一使用：

```ts
getRankByScore(score)
```

根据 Score 推导，用于成绩列表、B30 列表和后续导出显示。

#### 曲名

使用 Fuse.js 匹配曲库。

#### 难度

使用可选难度集合和当前歌曲已有谱面信息交叉校验。

### 8.4 OCR 结果处理

区分识别成功、识别失败和按规则跳过，不设置存疑 / 待复核状态。

通过字段解析、曲库匹配和业务规则校验的结果直接入库，不增加录入前确认页；未通过的结果按识别失败处理，不创建成绩记录，仅在失败后提示用户。

OCR 置信度仅可作为识别过程中的辅助信息，不持久化到成绩记录。具体识别通过条件与阈值仍待后续确定。

### 8.5 截图生命周期与隐私

截图仅在 OCR 处理期间驻留浏览器内存。

明确约束：

- 不将原始截图写入 IndexedDB。
- 不将原始截图写入 localStorage。
- 不将截图转换为 Base64 后持久化。
- 不在成绩记录中保存截图路径、Blob 或缩略图。
- OCR 完成或任务结束后释放 `File` / `Blob` / `ImageBitmap` / Canvas / Object URL 等引用。
- 离开识别页即取消未完成及排队 OCR 任务，取消后不再接收入库结果；已入库成绩保留。
- 页面刷新或关闭后，未完成任务中的截图无需恢复。

## 9. 成绩录入流程

### 9.1 单张 / 批量上传

用户可选择一张或多张成绩截图。

流程：

```text
选择截图
 ↓
加入 OCR 任务
 ↓
裁剪字段
 ↓
OCR
 ↓
曲名匹配
 ↓
字段校验
 ↓
写入 IndexedDB
 ↓
显示录入结果
```

### 9.2 识别失败

失败情况包括：

- 曲名无法匹配
- Score 无法解析
- Score 超出 `0 <= score <= 1,050,000` 的合法范围
- 谱面无法确定或业务规则校验未通过
- 截图结构无法识别
- OCR 异常

失败任务不创建成绩记录，也不修改已有成绩；仅在识别失败后向用户提示。失败状态与错误信息只用于当前运行时提示，不持久化。截图仍只在处理期间驻留内存，不做持久化。

不保留存疑标记，不提供待复核成绩列表。用户可通过手动新增录入未识别成功的成绩。

### 9.3 重复成绩

唯一逻辑键为：

```text
songId + chartId
```

对于同一曲目同一谱面再次通过 OCR 录入：

OCR 重复录入策略：

```text
新 Score > 已有 Score
    → 更新最高成绩

新 Score < 已有 Score
    → 保留已有最高成绩

新 Score == 已有 Score
    → 保留分数和已知字段，只补齐未知 FC / AP / Max Chain
```

一期只维护当前最高成绩，不记录每次上传或成绩变化历史。

手动编辑属于纠错操作，允许将已有 Score 调低，保存时必须警告用户并显示对应的曲目，Rank / Rating 将随之重新计算；不受上述 OCR 仅保留较高分的规则限制。

历史成绩、Rating 变化、更新时间线等能力待二期或后续单独设计，目前不提前固定数据模型。

## 10. 本地数据库设计

使用 Dexie.js 管理 IndexedDB。

### 10.1 scores

```ts
interface ScoreRecord {
    id: number

    songId: string
    chartId: string

    score: number
    fc?: boolean
    ap?: boolean
    maxChain?: number
    rating: number

    source: 'ocr' | 'manual'

    createdAt: number
    updatedAt: number
}
```

### 10.2 数据唯一性

同一：

```text
songId + chartId
```

只保存一条当前最高成绩；手动纠错允许将该记录的 Score 调低，保存时须警告用户。

### 10.3 派生字段与 Rating 持久化

以下数据优先根据基础数据实时计算，不作为用户可编辑的独立事实字段：

- Rank：由 Score 推导
- 是否进入 B30：按 12.7 节排序取前 30 个谱面；不同模式、不同难度均算不同谱面，同曲可有多个谱面入选。

这样可以避免修改 Score 后出现 Rank / Rating 不同步。

另外，Chart Rating 持久化为已截断到两位小数的值；录入或修改 Score 时重新计算并写回，列表与 B30 读取存储值，不作为用户可编辑的字段。记录 Rating 规则版本和曲库版本，任一版本变更时重算全部存量 Rating，并按两位小数截断后写回。重新计算后的数据用于 B30、Floor 和总 RT。

持久化计算版本元数据：

```ts
interface RatingCalculationMetadata {
    ratingRuleVersion: string
    songLibraryVersion: string
}
```

该元数据标识当前存量 Rating 对应的版本；完成全量重算后才更新版本标记，避免把旧 Rating 标记为新版计算结果。版本号格式与重算失败恢复细节仍需在实现规格中补齐。

### 10.4 不保存冗余曲目信息

成绩表原则上不重复保存：

- 曲名
- 歌手
- 等级

这些信息来自曲库，通过 `songId` / `chartId` 关联。

这样曲库修正翻译后不需要批量迁移历史成绩。

## 11. 一期页面设计

### 11.1 首页 / 识别页

功能：

- 拖入图片
- 点击选择图片
- 批量识别
- OCR 处理进度
- 成功 / 失败数量
- 识别失败后提示用户
- 跳转成绩管理

#### 识别进度弹窗与完成通知

选择或拖入图片后，通过弹窗展示批次进度、已处理数量 / 总数及每张图片状态，不再在首页内嵌进度列表。

- 原型只模拟这些状态，所有提示明确标记演示，不以识别成功或录入完成暗示已真实入库。

### 11.2 成绩管理页

功能：

- 显示当前最高成绩
- 搜索曲名
- 按模式 / 难度等筛选
- 手动新增成绩
- 编辑成绩
- 删除成绩

成绩管理与 B30 表格的面板顶部使用相同结构：左侧标题，右侧显示各自收录的谱面总数。两页的搜索与分类、模式、难度筛选紧接标题，下一行直接显示表格；筛选条件分别保存。成绩管理先对全部筛选结果排序，再按每页最多 30 条分页；修改筛选或排序后返回第一页。

实现时视情况使用 Naive UI `NDataTable`。

### 11.2.1 表格排序与分类筛选

成绩管理与 B30 表格支持点击表头在升序／降序之间切换，箭头标明当前方向。难度与等级共用单元格，分别提供排序按钮。艺术家与模式保留信息展示，不提供排序入口。等级将 `N+` 视为 `N.5`；难度升序为 easy < normal < hard < master；模式升序为 BASIC < ADVANCED；Rank 升序按第 12.4 节的等级顺序。Score、Rating 和原名次按数值比较，曲名按当前日／英文显示语言比较。

**成绩管理表格**

| 排序表头 | 比较优先级（从左到右）                                          |
| -------- | --------------------------------------------------------------- |
| 曲目     | 当前显示语言的曲名 → Rating → 等级 → 难度 → 模式                |
| 难度     | 难度 → 等级 → 模式 → Rating → 当前显示语言的曲名                |
| 等级     | 等级 → 难度 → 模式 → Rating → 当前显示语言的曲名                |
| Score    | Score → Rating → 等级 → 难度 → 模式 → 当前显示语言的曲名        |
| Rank     | Rank → Score → Rating → 等级 → 难度 → 模式 → 当前显示语言的曲名 |
| Rating   | Rating → Score → 等级 → 难度 → 模式 → 当前显示语言的曲名        |
| 更新时间 | `updatedAt`                                                     |

每级相同才比较下一级，升降序应用于整条比较链。所有比较项都相同时保留原有顺序，ID 不参与排序。默认按更新时间降序，最近更新的成绩优先显示；切换到曲目排序时默认升序，切换到其他表头时默认降序，再次点击同一表头切换方向。

成绩管理与 B30 的更新时间列显示月日和时分；非今年的记录额外显示年份。排序仍使用完整的 `updatedAt` 时间戳。

**B30 表格**

| 排序表头 | 比较优先级（从左到右）              |
| -------- | ----------------------------------- |
| 原名次   | 按第 12.7 节入选 B30 时确定的原名次 |
| 曲目     | 当前显示语言的曲名 → 原名次         |
| 难度     | 难度 → 原名次                       |
| 等级     | 等级 → 原名次                       |
| Score    | Score → 原名次                      |
| Rank     | Rank → 原名次                       |
| Rating   | Rating → 原名次                     |
| 更新时间 | `updatedAt` → 原名次                |

除曲目与原名次外，升降序只作用于选中的字段；字段值相同时始终按原名次升序排列，不使用 ID。B30 默认原名次升序；切换到曲目或原名次排序时默认升序，切换到其他表头时默认降序，再次点击同一表头切换方向。表头排序仅调整已入选记录的展示顺序，不重新选取 B30，不改变原名次、Floor 和总 RT。

B30 的搜索与筛选只作用于已入选的最多 30 张谱面；筛选后的行保留原名次，且不改变 B30 入选结果、Floor 和总 RT。

成绩管理增加歌曲分类筛选，可与曲名搜索、模式及难度筛选叠加。分类属于歌曲元数据，同曲不同谱面共享同一分类；以固定分类 ID 保存筛选值，日／英文名称跟随曲目信息语言切换，切换后不重置筛选。全部分类选项作为简体中文 UI 文案保留。

正式曲库的 `Song.genre` 按第 6.2 节定义保存以上分类 ID 之一；`Song.pack` 则独立表示免费曲包或 DLC 曲包名称。分类映射统一存放于 `src/data/categories.ts`。成绩展示层将曲库的 `genre` 映射到筛选字段 `category`；无成绩的分类显示空结果。

### 11.3 成绩新增与编辑

一期一并实现手动新增与编辑。新增时选择目标曲目、模式、难度并填写 Score；编辑时仅可修改已有记录的 Score，不更换曲目、模式或难度。

不可直接修改：

- Rank
- Rating

编辑时显示当前已有成绩的曲目与谱面；新增时使用可搜索列表选曲，再通过模式和难度按钮选择该曲目实际存在的谱面。

编辑列表仅用于定位已有成绩，不改变记录的 songId / chartId；不设置更换谱面或合并重复记录的流程。同一谱面始终只保存一条成绩。

Rank 与 Rating 在新增或修改 Score 后自动重新计算。

Score 必须为 `0 <= score <= 1,050,000` 范围内的整数，不合法时不允许保存。

手动编辑允许调低 Score。保存时若新 Score 低于该记录编辑前的 Score，必须警告用户并显示对应的曲目，Rank / Rating 将重新计算。

手动新增记录的 `source` 为 `manual`。

曲目选择提供可搜索的歌曲列表，模式与难度使用按钮；正式功能复用 Fuse.js / SongSearch。

#### 新增与编辑共用弹窗

新增与编辑复用同一份弹窗及表单，仅根据当前操作切换可编辑范围，不分别维护两套弹窗。

- 新增时通过搜索曲目名称／艺术家筛选歌曲，日英曲名均可搜索；显示当前已选曲目，搜索无结果时显示明确提示。
- 模式使用 `BASIC` / `ADV` 按钮，数据值仍为 `basic` / `advanced`；难度使用按钮，并按“难度名 等级”显示，例如 `MASTER 15`、`HARD 14+`。
- 新增默认选择 ADV、MASTER（MAS）。正式曲库应仅提供歌曲实际存在的谱面；若默认谱面不存在则禁用不可选项并提示选择有效谱面，不虚构谱面。
- 编辑时显示已有曲目，模式与难度按钮锁定，可修改 Score、FC / AP 与 Max Chain。
- 当前输入合法 Score 后立即更新 Rank 和单曲 Rating；Rating 区显示“歌曲定数 → 单曲 Rating”，例如 `14.5 → 16.34`。非法或空 Score 显示 `—` 并禁用保存。Rank 按第 12.4 节，Rating 按第 12 节计算，截断两位小数。
- 调低已有 Score 的警告保持不变。原型的谱面定数是演示配置，实时计算不代表已接入正式曲库或成绩存储。

## 12. 数据来源与规则定义

### 12.1 主要数据来源

当前计划使用社区站点 GrooveCoaster.Link 作为主要参考数据源：

- FP 曲库：  
  `https://groovecoaster.link/fp`
- Groove Rating 规则：  
  `https://groovecoaster.link/a/groove-rating`

截至 2026-09-20，该站 FP 页面列出 120 首歌曲，并包含日 / 英曲名、艺术家、谱面难度等资料。

### 12.2 曲库版本信息

在曲库数据旁维护 metadata：

```json
{
    "source": "GrooveCoaster.Link",
    "sourceUrl": "https://groovecoaster.link/fp",
    "verifiedAt": "2026-09-20",
    "game": "Groove Coaster: Future Performers"
}
```

后续新增 DLC / 游戏更新时更新曲库及 `verifiedAt`，并更新曲库版本。曲库版本和 Rating 规则版本均需明确记录；任一版本变更后，按 10.3 节重算存量 Rating。`verifiedAt` 仅表示核对日期，不替代版本标记。

### 12.3 Rating 基础规则

> 以下规则在一期实现，用于成绩列表的单谱 Rating、Groove Rating 与简单 B30 列表。

单谱 Rating：

```text
truncate2(x) = floor(x * 100) / 100（本文 Rating 均为非负数）

Raw Rating =
    0                                                   当 0 <= score <= 500,000
    (score - 500,000) / 200,000 * max(0, Chart Base - 3.5) 当 500,000 < score < 700,000
    max(0, Chart Base + Score Offset)                     当 700,000 <= score <= 1,050,000

Chart Rating = truncate2(Raw Rating)
```

其中 Chart Base 有如下换算规则，举例：

```text
14  → 14.0
14+ → 14.5
```

### 12.4 Rank 推导规则

Rank 只根据 Score 推导，不从 OCR 结果或用户输入获取。

项目采用以下阈值：

|        Score（含上下界） | Rank |
| -----------------------: | ---- |
|           `0 ～ 299,999` | E    |
|     `300,000 ～ 499,999` | D    |
|     `500,000 ～ 699,999` | C    |
|     `700,000 ～ 799,999` | B    |
|     `800,000 ～ 849,999` | A    |
|     `850,000 ～ 899,999` | AA   |
|     `900,000 ～ 949,999` | AAA  |
|     `950,000 ～ 999,999` | S    |
| `1,000,000 ～ 1,009,999` | S+   |
| `1,010,000 ～ 1,019,999` | SS   |
| `1,020,000 ～ 1,029,999` | SS+  |
| `1,030,000 ～ 1,039,999` | SSS  |
| `1,040,000 ～ 1,050,000` | SSS+ |

来源：[グルーヴコースター Wiki — Groove Coaster（SwitchFP版）/ ゲーム概要，スコアランク](https://www.wikihouse.com/groove/index.php?Groove%20Coaster%A1%CASwitchFP%C8%C7%A1%CB%2F%A5%B2%A1%BC%A5%E0%B3%B5%CD%D7)，核对日期：2026-09-22。表中阈值均含下界，Score 合法范围为 0～1,050,000 的整数。

原网页在 SS 起的高分段注明仅在启用 PERFECT+ 判定时可达到；理论满分仍为 SSS+。本工具按最终 Score 推导 Rank，不额外增加 PERFECT+ 设置字段。

前端统一调用 `src/core/rating/rank.ts` 的 `getRankByScore(score)`；包括演示列表在内，Rank 均由 Score 实时推导，不在演示数据或成绩记录中维护独立 Rank 值。非法 Score 应先拒绝，不能默认为 E 或截断到合法边界。

### 12.5 Score Offset

当前采用如下分段节点：

|     Score | Rank | Offset |
| --------: | ---- | -----: |
|   700,000 | B    |   -3.5 |
|   800,000 | A    |   -2.0 |
|   850,000 | AA   |   -1.5 |
|   900,000 | AAA  |   -1.0 |
|   950,000 | S    |   -0.5 |
| 1,000,000 | S+   |    0.0 |
| 1,010,000 | SS   |   +0.5 |
| 1,020,000 | SS+  |   +1.0 |
| 1,030,000 | SSS  |   +1.5 |
| 1,040,000 | SSS+ |   +2.0 |
| 1,045,000 | —    |   +2.5 |

相邻节点之间采用线性插值。本表仅用于 Score >= 700,000；更低分数按 12.9 节计算，不向下外推 Offset。

例如：

```text
Score = 1,035,000
```

处于：

```text
1,030,000 → +1.5
1,040,000 → +2.0
```

的中点，因此：

```text
Offset = +1.75
```

若谱面为 Lv.14：

```text
Rating = 14 + 1.75 = 15.75
```

### 12.6 单谱 Rating 上下限

单谱 Rating 最低为 0。先按 12.3 节的分段公式计算非负 Raw Rating，再截断到两位小数；不四舍五入。Score 在 0 至 500,000（含两端）时，单谱 Rating 固定为 0。

在合法 Score 范围内，1,045,000 分及以上获得：

```text
Chart Base + 2.5
```

该值即为最大单谱 Rating。

### 12.7 Groove Rating / B30

最终 Groove Rating 为：

```text
所有谱面已截断到两位小数的 Chart Rating
 ↓
从高到低排序
 ↓
取前 30 个，不足 30 个的部分按 0 计
 ↓
求和后除以 30
 ↓
将结果截断到两位小数，得到 Groove Rating（总 RT）
```

B30 按谱面取前 30 条；同一曲目的不同难度、不同模式均视为不同谱面，不按歌曲去重。

少于 30 条成绩时仍固定除以 30，不足部分仅在总 RT 计算时按 0 计；列表只显示已有记录，不显示空缺占位。没有成绩时 Groove Rating 显示 `0.00`，列表显示无成绩状态。

B30 Floor 取排序后 B30 列表最后一条已有记录的单谱 Rating；不足 30 条时仍取最后一条已有记录，不按补零值取 Floor。没有成绩时无可取记录，Floor 显示 `—`。Floor 与总 RT 同时显示在界面上，二者含义不同：Floor 为最后一条的 Rating，总 RT 仍按上述固定除以 30 的公式计算。

单谱 Rating 在存储、排序和求和前截断到两位小数；总 RT 必须使用这些已截断的单谱值计算，求平均后再次截断到两位小数。显示时固定两位小数（例如 `0.00`），不四舍五入。

计算口径：

```text
ratingCents = floor(Raw Rating * 100)
Chart Rating = ratingCents / 100
Groove Rating = floor(sum(B30 的 ratingCents) / 30) / 100
```

实现须避免二进制浮点误差使恰好落在百分位的值被错误截断；可采用精确分数或十进制定点运算，不在插值中间步骤提前截断。

B30 按以下顺序逐项比较，前一项相同才比较下一项：

1. 已截断到两位小数的 Chart Rating，降序。
2. Score，降序。
3. 谱面定数 level，降序。
4. 难度：master > hard > normal > easy。
5. 模式：ADVANCED > BASIC。
6. 日文曲名，降序。

所有比较项都相同时保留原有记录顺序，ID 不参与排序。B30 原名次按此顺序确定；固定使用日文曲名可避免切换界面语言时改变入选谱面及原名次。切换表头只改变展示顺序。

### 12.8 Rating 计算口径

本工具统一按照理论分段公式正常计算 Rating。

对于 `1,040,000 ～ 1,045,000` 区间：

- 正常进行线性插值。

### 12.9 700,000 以下的 Rating

按照已确定的项目口径：

- Rank 按 12.4 节推导：300,000 以下为 E，300,000～499,999 为 D，500,000～699,999 为 C；700,000 起为 B。Rank 与本节 Rating 公式分别计算。
- `0 <= score <= 500,000`：单谱 Rating 为 `0.00`。
- `500,000 < score < 700,000`：在 `(500,000, 0)` 与 `(700,000, max(0, Chart Base - 3.5))` 两个端点之间，对 Rating 本身进行线性插值。
- `score = 700,000`：衔接 12.5 节的 Offset 节点，Rating 为 `truncate2(max(0, Chart Base - 3.5))`。
- 计算结果统一截断到两位小数，并以截断后的值参与 B30 排序及总 RT 计算。

例如 Lv.14 谱面：

|   Score | 截断前 Rating | 最终 Chart Rating |
| ------: | ------------: | ----------------: |
|       0 |             0 |              0.00 |
| 500,000 |             0 |              0.00 |
| 500,001 |     0.0000525 |              0.00 |
| 600,000 |          5.25 |              5.25 |
| 699,999 |    10.4999475 |             10.49 |
| 700,000 |          10.5 |             10.50 |

例如仅有上述 `699,999` 分这一条成绩时，总 RT 为 `truncate2(10.49 / 30) = 0.34`，Floor 为 `10.49`，B30 仅显示这一条记录。

### 12.10 判定窗口

FP 判定窗口资料当前不参与本工具核心计算。

因此不写入业务算法，仅作为参考资料保留。

如未来增加判定分析、成绩详情分析等功能，再单独建立规则模块。

## 17. 设计原则

1. 一期完成 OCR 录入、Rating 计算和简单 B30 列表，B30 成绩图留到二期。
2. 业务数据以 IndexedDB 为唯一真实来源。
3. 一期离开识别页即取消 OCR，不引入 Pinia；跨页面后台队列留到二期评估。
4. 曲库通过稳定 ID 与成绩关联。
5. UI 语言与曲目元数据语言分离。
6. Rating 等游戏规则独立封装，不散落在组件中。
7. 第三方社区规则必须记录来源和核对日期。
8. 不为了未来可能的需求提前引入重型依赖。
9. 一期同时支持手动新增与编辑；编辑可修改已有记录的 Score、FC / AP 与 Max Chain，不更换曲目 / 谱面，调低分数时保存须警告；不增加 OCR 录入前确认流程，Rank / Rating 不提供手动修改。
10. 截图仅在处理期间驻留内存，成绩持久化。
11. 历史变化待后续独立设计，不在一期提前固定模型。
12. OCR 失败不记录成绩，仅在失败后提示用户；不保存存疑标记。
13. Score 为 0 至 1,050,000 的整数；单谱 Rating 最低为 0，0 至 500,000 分为 0，500,000 至 700,000 分按 Rating 端点线性插值；单谱值截断到两位小数后参与总 RT 计算，Groove Rating 不足 30 条按 0 补足、固定除以 30 后再截断到两位小数。
14. PWA 仅作为二期之后的未来设计选项。

## 20. 阶段 2、3 实施规格（2026-09-25）

阶段 2、3 已接入：124 首歌曲、992 张谱面；SongService、Fuse.js 搜索、Dexie 成绩持久化和真实手动 CRUD。保留当前维护中的 songs.json 内容，不在本次实施中重新抓取或改写曲库。曲目资料的准确性、收录完整性及封面下载不视为本次已逐首核验的结论。

### 20.1 稳定 ID 和曲库维护（T06）

- Song ID 为已有十进制字符串（目前 1～124），首次分配后永久保留；新增歌曲分配未使用过的递增 ID，不按数组位置、语言、标题或排序重新编号。
- Chart ID 全库唯一，格式 `{songId}-{mode}-{difficulty}`，例如 `1-advanced-master`；同一歌曲每个模式／难度最多一张谱面。
- 修改译名、别名、分类、等级不改变 ID。下架歌曲或谱面保留原曲库记录和 ID，以保留存量成绩关联；不删除、不复用。将来隐藏下架谱面的交互另行设计。
- 加载曲库时校验重复 ID、组合唯一性、模式／难度、分类及整数／半整数等级。成绩写入必须验证歌曲与谱面关联。
- 英文标题／歌手缺失时回退日文，vocal 与本地封面 coverUrl 可选；分类源字段统一为 genre，页面 category 为展示映射。

### 20.2 搜索（T07）

- NFKC 统一 Unicode／全角形式，英文字母转小写，`&` 替换为 ` and `，移除 Unicode 标点与符号，连续空白合并为单空格并去除首尾空白。
- 日英标题、searchAliases 和特殊曲名别名共同进入索引，另建无空格标题索引；艺术家日英名参与手动搜索。精确标题／别名优先，其余按 Fuse 匹配排序。空查询返回全部歌曲。
- Wire&Ring → wire ring / wire and ring；1nfinite 5tellar Chronicle → infinite stellar chronicle 等；III → 3；Destr0yer → destroyer / d0；FREE CONNECTION 2 支持文档列出的分词形式。
- Fuse 手动搜索 threshold=0.35、ignoreLocation=true。此阈值不用于 OCR 自动入库验收，T02 仍需 PoC 确定。展示始终保留原文。

### 20.3 写入语义（T08）

- scores 使用自增主键及唯一复合索引 `&[songId+chartId]`；不存储截图、标题、歌手、等级和 Rank。
- 新增、编辑、OCR 统一仅接受 0～1,050,000 的整数。Rating 使用已有精确计算模块自动计算；Rank 实时推导。
- 手动新增重复谱面报错，提示编辑已有成绩，不静默覆盖。编辑接口只接受记录 ID、Score、FC / AP、可选 Max Chain 和降分确认，不接受歌曲或谱面变更。
- 降分显示曲名和警告，须勾选确认；仓储再次检查确认参数。OCR 使用事务比较分数，只更新更高分，支持并发写入且不会产生重复记录。
- source 表示最近一次实际修改成绩字段的方式。createdAt 首次写入后不变；Score 或 FC / AP / Max Chain 实际变化才更新 updatedAt/source。较低 OCR 分数完全不更新；相同分数只补齐未知字段，不覆盖已知值。完全相同输入不更新。版本重算不改变时间或来源。
- IndexedDB 为唯一事实来源，Vue 使用 liveQuery 订阅读取结果，新增／编辑／删除后首页、列表和已有 B30 展示同步刷新。无演示成绩自动入库。

### 20.4 版本重算和异常（T10、T09 部分）

- 曲库版本格式 `YYYY-MM-DD.N`，规则版本使用 `MAJOR.MINOR.PATCH`，记录于 src/data/metadata.json；每次曲库数据变更递增曲库版本，计算规则变更递增规则版本。
- 数据库 schema 版本独立管理，当前为 1。启动时先检查计算版本；任一版本不同，在同一读写事务内重算全部 Rating，再更新 metadata 的 calculation 标记。
- 缺失关联或任何写入失败会回滚整次重算，保留原记录及旧标记；页面显示错误并提供重试，初始化完成前禁止保存／删除。
- 写入异常保留编辑表单并提示错误；只有事务成功才关闭表单并显示成功。IndexedDB 不可用时提示检查浏览器存储权限，不自动退回内存假保存。
- 运行时需要支持 IndexedDB、dialog、BigInt 的现代浏览器。移动端及各浏览器实机矩阵仍属 T09 后续验收，不在本阶段宣称全部验证。

### 20.5 验证

`yarn test` 验证 Rank／Rating 边界、整库 ID 与谱面关联、双语及别名搜索、非法分数拒绝、CRUD 和重开读取、重复新增、并发 OCR 最高分、降分确认、来源／时间语义及版本重算回滚。`yarn build` 执行 Vue／TypeScript 检查及生产构建。Edge 独立浏览器上下文已实测新增、刷新保留、编辑锁谱、降分确认、重复新增报错及删除；检查 390px 手机宽度布局。阶段 5 已替换截图 OCR 演示，实际识别与入库规格及验证见第 21 节。

### 20.6 本地数据与选曲交互补充

- 设置页“本地数据”提供清空成绩入口，显示成绩数量；确认弹窗明确无法撤销。确认后清空 scores，保留曲库、计算版本及外观偏好，列表／B30 通过订阅同步。失败保留弹窗并显示错误。
- 列表及选曲弹窗封面直接使用 coverSourceUrl；图片懒加载，失败显示音符占位，不依赖本地下载封面。
- 新增成绩默认折叠已选曲目，点击后向下展开搜索及结果；选中曲目自动收起并将焦点返回展开按钮。编辑时维持不可更换曲目的展示。


## 21. 阶段 5：真实截图 OCR 与入库（2026-09-25）

### 21.1 数据字段和兼容性

成绩新增可选字段 `fc?: boolean`、`ap?: boolean`、`maxChain?: number`。缺省表示未记录，不把旧成绩的未知状态推断为 false。AP 必须同时为 FC；Max Chain 为非负安全整数，手动新增／编辑允许留空。选曲页没有 Max Chain，保持缺省，不从谱面总物量推算。列表在分数下展示 AP／FC 和已有 Max Chain。

这些字段不参与索引，Dexie schema 仍为 1，无需破坏性迁移，旧记录可直接打开。成绩更高时附带字段随本次成绩替换；相同分数只补充未知值（例如先选曲页、后结算页补 Max Chain），不覆盖已知值、不接受矛盾 FC／AP。较低成绩不修改记录。手动纠错允许修改以上字段，曲目／谱面仍不可更换。

### 21.2 布局、ROI 和判定（T01、T02）

支持完整 16:9 的英文／日文结算页 `result` 和选曲页 `select`。先识别左上角 Results／リザルト／Select Song／楽曲選択，再读取对应字段；无法确认布局直接跳过。playing 不视为成绩图。

ROI 位于 `src/core/ocr/recognizer.ts` 的 `regions`，表中为 1280×720 基准像素的 x、y、宽、高，代码除以 1280／720 保存归一化坐标：

| 字段 | result | select |
| --- | --- | --- |
| 页标题 | 45, 8, 205, 38 | 同左 |
| 曲名 | 150, 55, 478, 37 | 57, 309, 453, 43 |
| 状态 | 275, 184, 690, 103 | 1036, 449, 80, 37 |
| Score | 202, 315, 365, 72 | 792, 440, 236, 52 |
| Max Chain | 470, 473, 91, 41 | 不存在 |
| 模式 | 824, 136, 127, 26 | 1072, 625, 134, 32 |
| 难度 | 619, 109, 96, 32 | 识别下方卡片的粉色高亮上边框 |
| 等级 | 720, 102, 74, 52 | 527, 322, 55, 34 |

结算 Score 按基准原尺寸识别，其他文字 ROI 放大两倍。结算页读取本次大号 Score，不读取 HIGH SCORE。选曲页读取右侧 HIGH SCORE；难度不能仅由等级反推，先用四张难度卡片高亮位置确定难度，再与左侧等级、模式和曲库交叉验证。颜色阈值与最小差距在识别器中集中配置，无法唯一确认时失败。

状态 `MISSION CLEAR`（兼容 `MISSON CLEAR`）在读取曲名／分数前直接跳过，不新建、不更新任何成绩。FULL CHAIN → FC，ALL PERFECT → AP + FC，CLEAR / FAILED → 无 FC / AP。未知或不完整状态失败，不把它默认为 CLEAR。选曲页 0 分且无完成状态视为未游玩占位并跳过。

数字进行 NFKC、空白移除及 O→0、I/l→1 校正。有逗号时严格校验千位分组，避免漏识别数字后组成合法低分；非法字符、超范围分数均失败。曲名仅以日英标题和已有别名进行 Fuse 匹配，不使用艺术家匹配；精确匹配优先，模糊候选分值 ≤0.20、与次候选差距 ≥0.08。模式、难度、等级必须唯一对应库内谱面。文字识别最低置信度为 0.65，置信度不持久化。

### 21.3 上传、任务和资源（T04、T09）

- 首页上传入口执行真实 OCR；每批最多 30 张，PNG／JPEG／WebP，每张 1 字节至 20 MiB。解码后要求宽度 ≥960px、像素 ≤16,777,216、宽高比与 16:9 差值 ≤0.025。
- 串行处理，显示排队、识别中、已处理、失败、跳过。成功数表示通过校验且数据库事务完成的图片数，重复低分也算已处理，不宣称新增同等数量记录。
- 完成统计分别显示已处理／失败／跳过。失败或跳过时保留结果，用户可关闭后重新选择图片；不保存截图以实现一键重试。全成功显示完成动画和通知。
- 单图模型加载／识别超时为 120 秒；模型或运行时异常显示失败，可重新选择图片重试。数据库未就绪禁止导入，写入失败不得显示成功。
- 关闭弹窗、切换页面、组件卸载时终止 Worker、取消排队并释放 File、ImageBitmap、Canvas 引用。异步结果和仓储事务均检查取消信号；取消后的结果不能入库，已提交记录保留。新批次使用独立代次，旧批次回调不得关闭或推进新批次。
- 使用官方 `@paddleocr/paddleocr-js` 0.4.2、PP-OCRv5 日文兼容模型、WASM 单线程 Worker。首次需联网下载官方模型，图片不上传。SDK 内部依赖 OpenCV.js，与应用自身 Canvas 预处理区分。
- SDK 预构建 Worker 内含 ORT 1.24.3，因此显式固定配套 `onnxruntime-web` 1.24.3。`scripts/prepare-ocr.mjs` 在 dev/build 前复制 Worker 和 WASM 到忽略提交的 `public/ocr`，支持 Vite 子目录 base；不依赖未固定版本的 CDN WASM。更换 SDK 时须同步核验内置 ORT 版本。
- 已验证本机 Edge；运行时要求 Worker、WASM、Canvas、createImageBitmap、AbortSignal.any/timeout、IndexedDB。其他浏览器和移动设备性能尚未实机验收。

SDK API 依据：[官方 PaddleOCR.js 文档](https://github.com/PaddlePaddle/PaddleOCR/blob/main/paddleocr-js/packages/core/README.md)。

### 21.4 固定样本与结果（T03）

`tests/ocr-samples.json` 保存逐张人工标注预期；图片为本地 `src/data/test`，按现有 gitignore 不提交。21 张含 result 10 张、select 8 张、playing 3 张。目标：15 张有效成绩整条字段均正确；2 张任务结算、1 张未游玩占位、3 张游玩中图片全部跳过；错误入库为 0。

本机 Edge 真实 OCR 实测达到上述目标：有效曲目匹配、Score、模式／难度／等级、FC／AP、结算页 Max Chain 均为 15/15；6/6 负样本跳过。批量入库后去重得到 11 条谱面成绩。曲名原始文本完全一致不是 100%（存在空格和标点噪声），业务匹配后均正确。样本覆盖日英 UI、NORMAL/HARD 和 BASIC/ADVANCED；不将该结果外推为 EASY/MASTER、拍照、裁切、所有分辨率或所有曲目已通过。

T01～T04 按本节实现；T09 仍保留跨浏览器／移动端兼容性验收，不宣称全部环境已验证。
